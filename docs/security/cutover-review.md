# Cut-over review: identity v2 (I-15), roadmap item R2.8

- **Date:** 2026-11-01
- **Reviewer:** independent agent, read-only. I did not write this code.
- **Scope:** `git diff m1-baseline..identity-v2-cutover` over `plugin/server`, `plugin/shared`, `plugin/client`, `plugin/index.server.ts` and `plugin/index.client.tsx`, with emphasis on commit `095e24d` (tag `identity-v2-cutover`). The working tree was clean and HEAD equalled the tag, so everything below refers to committed code.
- **Context read:** `docs/design/implementation-plan-identity-v2.md` (I-15 and Follow-ups), `docs/security/hardening-plan.md` (all decision rounds), `docs/design/usability-roadmap.md` (R2.8).
- **Executed:** `npm run typecheck` (clean), `npm run typecheck:client` (clean), `npm test` (343 of 343 pass). `npx tsc --noEmit --noUnusedLocals` (no files written) to look for dead imports. A grep of the unit test output for `prc2.`, `prg2.`, `prl2.` and `prk2-` patterns found no hits. No daemons, no network, no `~/.paseo`.
- **Not executed:** the e2e suites (`test/e2e-v2/run.sh`, `migration-run.sh`). Every finding comes from reading code. None was demonstrated at runtime.

## Verdict

The cut-over is sound. I found no secret leak, no viewer-reachable owner RPC, and no weakening of the Room Profile filter, the field allowlists, the lane endpoint limits, the viewer error policy or the project-name default. The development switches are gated correctly. Confirmation tokens are single use, expire, and are bound to the action and room.

One medium issue should be fixed before release. The session_open isolation tripwire for M1 fork agents left by the migration fails open whenever the migration record is not loaded. The remaining findings are low or informational: hardening, robustness of the migration in rare paths, and dead code.

Counts: 0 high, 1 medium, 5 low, 4 informational.

## What I checked and found clean

**Leftover v1 paths.** No production file imports or names the deleted modules: `host-store`, `control-server`, `control-client`, `invite-code`, `shared/control`, `shared/schemas`, `server/crypto`, `server/grants`, `paths`, `runtime`. `PASEO_ROOMS_PROTOCOL` and the M1 RPC contracts are gone. The only remaining `prc1.` references are the intended upgrade message and the decoder refusal (`invites.ts:73`, `v2-member.tsx:79`). The lane endpoint closes any first frame other than `hello`, and the control-channel mode was removed completely. The remaining dead code is listed in V-8.

**Room Profile.** `profile/*.csv`, `room-profile/filter.ts` and `generated.ts` are unchanged since `m1-baseline`. The only change to `sanitize.ts` (X-14 drive root, error references) still replaces every viewer-facing error with generic text. `plugin.rpc.invoke.request` and all other `plugin.*` requests stay default deny. Plugin RPCs, including `rooms.v2.lane.errors` and every admin action, are therefore unreachable from a lane viewer.

**Viewer error and project-name policy.** v2 endpoints get `errorRefs: true`. Error references are random (`randomBytes`). Full text is kept in memory only and served only by the local owner RPC. The `LaneEndpoint` default for `projectNames` is now `show: false` (previously it read HostStore). `LaneService` passes `namesShown(state, laneId)` from the fold.

**Lane endpoint limits.** `V2_LANE_LIMITS`, the failure token bucket, one link per device (`admitLink`), 32 routes per link, `assertOwnerUidLaneIsWatchOnly`, and grant checks on link hello, link open and every routed hello are all unchanged by the cut-over. `limits.ts` changed only its import.

**Agent guard.** It is registered by the v2 entry with `isReady = state === "ready"` (fail closed). The provider allowlist is unchanged. C-13 is ported: `agent.archived`, or an archived or missing agent at start, stops the endpoint, and the `gone` set prevents a restart in the same process. `lane.closed` is signed only when this daemon holds an admin key, and a failure is caught and logged.

**Development and test switches.** `gateDevSwitches` removes every `PASEO_ROOMS_DEV_*` unless the home passes `testHomeRefusal`: realpath under `.test-homes/v2-<name>`, not `~/.paseo`, and an owner-held regular marker file with exact content. Production constructs `RoomsRuntimeV2()` without `allowDevSwitches`. Every consumer of the dev switches receives `this.env` (see V-7). The test clock RPC is registered only when `rt.clock.enabled`, the clock is checked again in `advance`, moves forward only, and is capped at 7 days. `PASEO_ROOMS_RELAY_TLS=false` is honoured only for loopback hosts. The exception is V-3.

**Confirmation tokens.** Tokens are 32 random bytes and in memory only. The token is deleted before any check, so it is used once even when refused. The 5-minute expiry is checked on take. The token is bound to `actionKey` (canonical JSON including `roomId` and `kind`, with `compromise` normalised and lanes sorted) and to a subject recomputed at take time (`stale_base` on change). `handleAdmin` builds the bound action from the same parsed input that it passes to the handler, so the values signed are the values confirmed. The schema requires the token (`^[A-Za-z0-9_-]{43}$`). All 18 admin-statement actions are wrapped in `handleAdmin`. The ungated calls (invite revoke, join reject, own rekey, veto, `recovery.act`) match the I-14 decisions. Same-user callers can mint tokens, which is documented in S-12.

**index.server.ts gating.** Every handler goes through `handle`, which attaches the PaseoApi and logs only the method and a truncated error message. `rooms.migration.keys.delete` requires `confirm: true` in both the schema and the handler. The test clock registration is conditional. The cleanup function removes all three hooks and stops the runtime. `void rt.start()` cannot raise an unhandled rejection because `start()` catches.

**Secrets in RPC responses, errors and files.** Invite, link and recovery codes are returned once, by design. Status views expose ids, times and `gid` but never tokens (`GrantV2View`). Error constructors in `invites.ts`, `device-link.ts`, `invite-check.ts`, `genesis.ts` and `grants.ts` use codes, not input text. Grant logs carry `gid` only. The unit test output contained no v2 secret prefixes.

**Migration (`server/migration/v1.ts`).**
- Detection is specific to v1. v2 does not use `gateway/`, and only `member/rooms` and `member/settings.json` are protected as v2 entries, which matches every v2 path under `member/`.
- What it reads is recorded before anything moves.
- Renames are retried only on win32, only for EPERM, EACCES and EBUSY, with a bounded backoff of about 6 s, after which the part stays pending.
- Host-registration cleanup removes only entries with source `plugin:rooms` and a 16-hex v1 lane id, so v2 registrations (32 hex) cannot be hit. Removal throws before the record is marked done.
- Keys are deleted only on the explicit two-step UI action. The logs and `rooms.json` are kept. `lstat` excludes symlinked final components and archive directories.
- The start-time `verifyTree` (no symlinks) runs before the migration.
- Re-running is idempotent once nothing is left to move.
- I confirmed against `m1-baseline` that M1 grants lived only in the daemon's `hosts.json` and that the three archived key files are the only M1 key-bearing files.

The exceptions are V-4 to V-6.

**Durable writes and file protection.** `migration.json` and the agent-guard files use `writePrivateFile` from `platform/durable`. Archive directories are created with mode 0700. The start-time check runs before any key is read, and `rooms.permissions.fix` repairs without silently changing symlinks or foreign owners.

## Unresolved issues and next steps

1. Fix V-1 and add the failing-start test. This is the only item I would block a release on.
2. V-2 and V-3 are small changes that restore the intent stated in the commit message.
3. V-4 to V-6 affect rare migration paths: a same-day downgrade, a crash between renames, and a partial win32 move. The existing migration unit tests can cover them with an injected `renameSync`.
4. The e2e suites were not re-run in this review. The commit reports 107/107 offline, 105/105 live relay and 19/19 migration. I did not verify those numbers.
