# paseo-rooms: protocol and design review before Milestone 2

- **Date:** 2026-10-28
- **Reviewer:** independent (did not build M1). Read-only review: no code changed, no daemon run, nothing installed.
- **Scope:** `research/rooms-architecture.md` (v2), `plugin/docs/specs/*`, `plugin/M1-RESULTS.md`, `plugin/README.md`, all of `plugin/server` and `plugin/shared`, and the Paseo source at `/tmp/lab-connect-research.TYTc/getpaseo_paseo` (main, 0.14.0-beta.2, commit `1467121b`). The published 0.13.2 protocol in `plugin/node_modules/@getpaseo/protocol` was checked where it matters.
- **Method:** each area was threat-modelled against eight attackers: a curious or malicious room member, a revoked member, a holder of a stolen invite or credential, a network or relay adversary, a compromised member daemon, other installed plugins on either daemon, a malicious owner, and a prompt-injected room agent.
- **Evidence labels:** "verified in code" means I read the cited lines. "Inferred" means the conclusion follows from the code but I did not execute it. Nothing here was exploited live.

## 1. Summary

M1 is carefully built for what it claims: a watch-only lane, a default-deny Room Profile, a pushed revocation path and honest documentation of its deviations. The Room Profile filter and the control protocol's transcript binding are sound for M1. I found no way for a member to read another agent, or to act on the owner's daemon, through the lane protocol itself.

The problems are mostly about what M2 will build on top:

1. **Who a member is.** Membership identity is "whoever held the invite first". The label is self-asserted, and nothing is verified out of band. Each key is a plaintext file readable by any process of the same OS user. MLS credentials attested on this basis inherit all of these weaknesses, and the encryption-at-rest planned in M1-RESULTS section 8 item 5 protects nothing against those processes, because the key is derived from a file in the same directory.
2. **The scope of membership.** In M1 a member is a (lane, member daemon) pair, while the MLS group is per room. M2 needs a room-level member, a device record, an admin authority separate from the host, and a roster rule that makes MLS group membership match signed membership. Without these, the host (once standalone) or anyone holding the host key can add ghost devices.
3. **The room log.** It is host-signed only, so member actions are not attributable to the member's key. A host can also show different logs to different members (fork) or drop the newest events (truncation), and nothing anchors the log to MLS epochs. The envelope format will freeze when MLS content goes into it.
4. **Agent isolation is not a security boundary.** The inert `paseo` MCP shadow removes one tool surface. A room agent with a shell can still do all of the following:
   - read `local-credential` and drive the whole daemon through the `paseo` CLI;
   - read other agents' MCP bearer tokens from `/proc/*/cmdline`;
   - read the host key, lane keys, device key and grants;
   - inherit MCP servers from the provider's user or project config;
   - receive MCP servers from other plugins' hooks, which run after `rooms` in alphabetical order (and on 0.14 also through `agent.open.before`).

   This must be fixed with an OS-level sandbox before any member-authored text reaches an agent.
5. **The grant is a bearer token** on the host link. One design detail lets a thief prolong its use: the thief's routes count as the member's `activeRoutes`, so the member's idle-only rotation is deferred until expiry, up to 7 days.

**Counts:** 0 critical, 9 high, 12 medium, 8 low (29 findings). **Ten block M2** (section 2, "Blocks M2?" = yes; P-29 is folded into P-3). Most M2 blockers are cheap to fix now but expensive once MLS formats and credentials ship.

## 3. Spec and implementation mismatches

| # | Where | Spec or doc says | Code does |
|---|---|---|---|
| M-1 | arch §3, §8.1 | RoomEvents "signed by its producer (host or gateway)"; "every key change is a signed, logged event" | All events signed by the host key, including member actions. There are no key-change events. Not listed among deviations D1-D7. |
| M-2 | arch §10 | "Seated agents have Paseo's control MCP removed **and a restricted tool policy**" | Only the MCP shadow, plus removal of `toolPolicy` preapprovals. No restriction on shell, files or other MCP servers (P-5, P-6). |
| M-3 | spec control §4 | Burned invite: `invite.status = "burned"` | No status field. "Burned" is derived from `revokedAt` + `failedAttempts ≥ 5` (`host-store.ts:284-289`), and the burn is not logged. Functionally equivalent, but the spec reads like a stored field. |
| M-4 | `schemas.ts:132` comment | `prev`: "Hex sha256 of the previous event's `hash`" | `prev` is the previous `hash` itself (`event-log.ts:29`). data-model §4 is correct; the comment is wrong. |
| M-5 | spec control §3 | "Member to gateway: the member signs … proves possession" (implying it authenticates *the member*) | Authenticates the presented key only. Member lookup is by 64-bit key id, and the signature is checked with the presented key, not the stored one (P-22). |
| M-6 | data-model §5 | `member/rooms.json` "Secret: no" | Not secret, but **integrity-critical**: it holds the pinned host key and lane static key. Whoever can modify it decides whom the member trusts. Same for `gateway/state.json` (also holds lane secret keys, correctly marked). |
| M-7 | arch §6.1, §8.2 | "Revocation is checked on every hello and cuts live sessions" | True on the happy path. Not enforced if `save()` throws (P-13). |
| M-8 | spec control §7.3 | "No rate limit per source beyond invite burning" | Accurate, but it omits that burning is itself a DoS lever for non-invitees (P-15), and that `renew`/`status` are not limited at all (P-17). |
| M-9 | arch §8.2 row 1 | "Member authenticated by a lane-scoped signed grant per member daemon" | Correct, and D3 notes the bearer nature. Not stated: the grant also authorizes every client of that daemon (P-21), and a stolen grant suppresses rotation (P-9). |
| M-10 | room-profile §3 | "Inbound … forward" for allowed types (implied: as validated) | Forwards the viewer's object unchanged apart from the id checks. The upstream hello carries viewer fields (P-18). |

All other spec statements I checked match the code: frame shapes, transcript fields, the order of enrollment checks, the grant checks on link hello, link open and routed hello, pushed revocation, the 128-route cap, binary drop, clientId derivation, feature-flag sets and `hosts.*` denial.

## 4. Recommended changes

### 4.1 To `docs/specs/rooms-control-protocol.md`

1. §3: add "authenticates possession of a self-generated key; it does not identify a person". Add the SAS or owner-approval step (P-1) and `pending` membership.
2. §3: move the signature check before membership lookup, and define a single unauthenticated error (P-23).
3. §4: per-invite failure counting keyed by `inviteId`; a per-lane token bucket; a rate limit on `renew`/`status`; an `invite.burned` event (P-15, P-17).
4. §5: accept only the member's current `gid`; at most one live link per member, with theft detection; a deferral cap on rotation (P-9, P-12).
5. §7: add the known limits "plaintext keys readable by same-user code" (P-2), "relay server-role takeover" (P-16) and "grant admits all daemon clients" (P-21).
6. Declare v1 one-shot only. Specify v2 (M2 delivery service) with mutual Noise XX/IK or handshake-hash binding (P-8), a version floor (P-25), and a room endpoint separate from lane endpoints (P-4).

### 4.2 To `docs/specs/data-model.md`

1. Add `RoomMember`, `Device`, `LaneAccess`, `AdminKey` and a device denylist. Define the scope of revocation (P-4, P-14).
2. Grant: full-key or 128-bit `dev`; `ctx`-prefixed signature input; JCS with test vectors (P-11, P-22).
3. Event log: producer signatures, new event types (`key.rotated`, `invite.burned`, `grant.suspected_theft`, `member.confirmed`), and a head-anchoring rule with MLS (P-7, P-10).
4. Storage: mark the integrity-critical files. State the OS-user trust boundary, and the backup exclusion and keystore plan (P-2, M-6).
5. Plaintext metadata inventory for M2. These should move inside MLS: `room.created.name`, member `label`, `lane.created.agentId` and `parentAgentId`, `laneServerId`, and invite expiry. These stay in the signed plaintext envelope: `roomId`, `seq`, `prev`, `hash`, event type (or a coarse class), `memberId` and `epoch`. Note that the event type and timing of membership events still leak the shape of the room to the host.

### 4.3 To `docs/specs/room-profile-v1.md`

1. Field-level allowlists for forwarded inbound messages and the upstream hello. A schema-shape hash in the generator gate (P-18).
2. Limits: links per member, routes per lane, timeline `limit` clamp (P-17).
3. State the content-level exposure of share-live lanes and fork context (P-19).

### 4.4 To `research/rooms-architecture.md` (proposed, not applied)

1. **§8.1 keys:** add an **Admin key** row (signs membership decisions; held by admin devices) separate from the **Host key** (orders, stores, signs transport-level records). The MLS authentication service checks admin-signed membership plus proof-of-possession, and members enforce roster = signed membership (P-3). Add a per-room member key certified by the device key (P-14). Add a key rotation and recovery paragraph (P-10).
2. **§8.1 identity binding:** state that M1-style invite enrollment binds a key, not a person. Make an out-of-band fingerprint or SAS confirmation part of enrollment from M2 (P-1).
3. **§8.2:** add "Member plugin ↔ lane endpoint (M1 control protocol v1)" (as M1-RESULTS proposes). Add "grants are bearer on the host link; theft detection by single-link policy". Add "every client of the member daemon can open routes" (P-9, P-21). Add relay server-role takeover to the threat table (P-16).
4. **§8.3:** replace "Host stores ciphertext only" with an explicit plaintext metadata list (section 4.2 item 5). Add "the room log head is bound into MLS commits; members gossip heads to detect forks" (P-7).
5. **§8.5:** replace "Encrypt persisted group state at rest" with "Persisted group state is protected only against offline disk and backup exposure, using a key that is not stored beside it (OS keystore). Same-user processes, including agents and other plugins, are inside the trust boundary." (P-2)
6. **§10:** rewrite "Confused deputy through Paseo's own MCP". Shadowing removes one surface. Isolation requires running room agents under an OS sandbox without access to `PASEO_HOME`, the daemon socket or `/proc`. Plugin hooks that run later (alphabetical order, `agent.open.before`) can re-add tools (P-5, P-6). Add rows for "Other plugins on either daemon (fully trusted; detection only)", "Malicious owner spoofing hosts in the member's app" (P-20) and "Host equivocation" (P-7). Change "Compromised host … caught by pinned keys" to depend on the admin/host key split (P-3).
7. **§3 / §4:** make membership room-scoped, with lane access as a sub-grant. Revocation scope must be explicit (P-4).
8. **§11 upstream proposals:** add proof-of-possession or channel binding for connected-host passwords, relay server-role authentication, per-plugin permission scoping and a final hook phase, route permission per origin session, and exposing the Noise handshake hash.
